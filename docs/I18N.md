# Internationalization

## Goals

Double Agent should be understandable worldwide without fragmenting its machine
interfaces. English is the canonical language. User-facing text can be
localized, while API fields, schemas, logs, state values, CLI flags, source code,
and identifiers remain stable English contracts.

## Supported locales

| Locale | Status | Coverage |
|---|---|---|
| `en` | Canonical | README, specifications, Web preview |
| `pt-BR` | Initial translation | README, specification snapshot, Web preview |

Locale matching normalizes `en-*` to `en` and `pt-*` to `pt-BR`. Unknown or
incomplete locales fall back to English per key.

## Web UI behavior

Resolution order:

1. explicit user preference stored in `localStorage`;
2. authenticated profile preference when a backend exists;
3. browser `navigator.languages`;
4. English fallback.

The selector uses native language names (`English`, `Português do Brasil`) so it
remains usable if the current locale is unreadable. Changing the language:

- updates visible strings without reloading;
- persists the preference;
- updates `<html lang>`;
- preserves the current route and form state;
- announces the change to assistive technology.

## Catalog conventions

- UTF-8 JSON files under `web/locales/<locale>.json` for the preview;
- nested semantic keys such as `hero.title`, never English sentences as keys;
- English catalog is complete and authoritative;
- every other catalog must have key parity in CI;
- missing or invalid values fall back to English;
- variables use named placeholders in the production framework;
- pluralization and dates use `Intl`, never string concatenation;
- no HTML from translation files.

The production React UI should adopt FormatJS, i18next, or another maintained
ICU-capable library after the frontend scaffold is selected. The dependency is
chosen through an architecture decision record, not embedded into API contracts.

## Documentation layout

```text
README.md                    canonical English
README.pt-BR.md              Portuguese overview
docs/*.md                    canonical English specifications
docs/pt-BR/*.md              Portuguese translation snapshot
```

Every translation identifies the canonical source and should record the commit
it matches once releases begin. English changes may merge before translations,
but the UI and docs must visibly indicate incomplete translation coverage.

## MCP and API

JSON field names, tool names, resource URIs, error codes, state values, enum
values, and audit event types are English-only. Optional human-facing strings may
accept a BCP 47 `locale` hint. Servers must always provide an English message and
may additionally provide localized text, for example:

```json
{
  "code": "capability_unavailable",
  "message": "The requested GPU backend is unavailable.",
  "localized_message": "O backend de GPU solicitado não está disponível.",
  "locale": "pt-BR"
}
```

Clients must branch on `code`, never on either message.

## CLI and logs

The initial CLI and all operational logs are English. A localized CLI may be
added later, but commands, flags, machine-readable JSON, environment variables,
and exit codes never change by locale. This keeps support, automation, and log
search reliable.

## Translation workflow

1. change the English source and catalog;
2. run catalog-key and link validation;
3. update translations or mark them pending;
4. require human review for authentication, authorization, billing, privacy,
   destructive actions, and security warnings;
5. test keyboard navigation, screen readers, text expansion, and mobile layout;
6. credit translators without exposing personal information.

## Adding a language

1. copy `web/locales/en.json` to a valid BCP 47 locale filename;
2. translate values without changing keys;
3. register the locale and native name in `web/app.js`;
4. add translated documentation under `docs/<locale>`;
5. add the locale to automated parity and fallback tests;
6. obtain review from a fluent human before claiming full support.

Validate the preview catalogs with:

```bash
node web/test-i18n.mjs
```

## Accessibility and directionality

All selectors are keyboard accessible and labeled. Layouts must tolerate at
least 35% text expansion. A future right-to-left locale sets `dir="rtl"` at the
document level and is tested as a complete layout mode, not by mirroring icons
or code blocks blindly.
